## What the project is

Twinfang is a Devil May Cry-style character-action prototype in the browser: Three.js r160 from a CDN, one built file `twinfang.html`, authored as parts in `src/` and concatenated by `python build.py`. Everything is generated by code at load: models, textures, animation, audio. No asset files.

Scope: a corridor with two fights, the Gatewarden boss in a hall, a winding stair, three sealed rooms, the Stormvane boss on the roof. Three weapon sets (Twin Fangs, Blade & Pistol, Great Maul), four enemy types (Husk, Brute, Stalker, Lantern).

The owner designs and playtests; Claude writes the code. They prefer a plain summary of what changed and what was not checked over a description of effort.

## What this rebuild was for

The owner saw Saltline, a one-shot browser FPS built by Claude Fable 5.2 where all art is code, and wanted Twinfang rebuilt toward that quality: much better graphics and sound, improved movesets, and **everything that can be mechanical made mechanical**, because hard-surface machines are far easier to build from code than people, hair or cloth.

Lessons taken from reading Saltline's source, which shaped this work:
- Textures are baked on the GPU at load by a shader per material, then fed to standard PBR materials.
- Sounds are synthesised into buffers at load, several variants each, and played through generated convolution reverbs.
- The game carries its own test harness (showcase, fixed camera, bench, error capture) so an agent can look at its own output. That is what makes long unattended work possible.
- Enemy attacks are limited by a token system. Twinfang already had one (`G.tokens`, `G.maxTokens`).

## What was done

Kept as it was: collision and level layout (`AREAS`), player logic, camera, input, combat data, boss logic, all animation clips, the rig's pose format and IK.

Replaced or added:

| Area | State |
| --- | --- |
| Materials (`04-textures`) | Seven GPU-baked sets: floor, wall, plate, armor, steel, rubber, hazard. `pbr(set, opts)` for characters, `worldMat(set, opts, wet)` for the level (adds large-scale variation and, on the roof, puddles with rain rings). Geometry carries UVs in metres divided by `TILE[set]`. |
| Renderer (`03-renderer`) | HDR scene with 4x MSAA, GTAO, a guard pass, UnrealBloom, then one final pass doing lens effects, ACES tone map and grade. Uniform names used by `14-game` are unchanged. `?q=low` and `?q=high` tiers. |
| Level (`05-world`) | Rebuilt from a kit (`sbox`, `scyl`, `sgeo`, `pipe`, `pillar`, `lamp`, `emblem`, `cog`, `shaft`) that collects geometry per material and merges it (`flushInto`). `dyn()` builds moving parts (door leaves, cogs). `CAST=false` around ceiling-level parts, because the "moon" light is a fake key light that must pass through ceilings. |
| Characters (`07-rig`, `10-data`) | Hero, Husk, Brute, Stalker and Gatewarden rebuilt as plated automatons. Parts are added per bone with `add(...)`, then `bake()` merges each bone's parts per material and caches the result per kind. `limbs()` is shared by hero and foes. Lantern and Stormvane only got new materials. |
| Audio (`02-audio`) | Rewritten. Recipes in `R` synthesise 26 sounds in 66 variants in time slices after the first click. Hall and roof reverbs, ambience beds, music ducking. The public methods (`sfx.hit`, `sfx.whoosh`, ...) and the music sequencer's riff are unchanged. |
| Movesets | Husks and Stalkers sometimes chain a second attack (`chain` in `11-enemy`). Brutes below 55% health add a shockwave to the slam. Wreckage on enemy death (`fx.debris`). Dodge thruster burst. Chest and head follow the pose through springs (`SPR` in `07-rig`), which gives every clip follow-through. |
| Harness (`15-harness`) | `?show=`, `?tp=`, `?cam=`, `?bench`, `?nan`, `window.HX`, build stamp on the title screen. |
| Tools (`tools/`) | Headless Playwright runner and scenarios: bot playthrough, audio bank check, invalid-pixel check, scene and showcase screenshots. |

## How it was verified, and the limits of that

All testing ran in headless Chrome with **software rendering on Linux**. On that setup:
- The bot in `devtest.js` completes all seven encounters with zero errors. It refills its own health and drains boss health on a timer, so this proves the game does not break, not that it is fair or fun.
- Every sound buffer synthesises without NaNs and with sane peaks.
- Screenshots of every area and character were reviewed.

Never verified:
- **Anything on the owner's GPU** (RTX 4070 Super, Brave on Windows, Direct3D through ANGLE). The one real-hardware report so far was a serious bug that the software renderer could not show.
- **How any sound actually sounds.** Nobody has listened with a critical ear and reported back.
- **Frame rate.** `twinfang.html?bench` exists for this; no numbers have come back yet.
- **Combat feel and difficulty**, including the new enemy follow-ups and the Brute shockwave.
- **The `tools/` scripts on Windows.**

## Open problems, in priority order

1. **Black blocks on screen (fix delivered, unconfirmed).** On the owner's PC large black rectangles covered part of the view. Cause found: the light-shaft shader in `05-world` called `pow()` on an interpolated UV that goes slightly negative at polygon edges under MSAA. Direct3D returns NaN for that, and bloom's blur pyramid spreads one NaN pixel into a block hundreds of pixels wide. Three layers of fix are in build `2026-11-18.3`: the shaft clamps before `pow`; every lit material ends with `GUARD` (`04-textures`); a pass before bloom zeroes or caps invalid pixels (`03-renderer`).
   If the owner still sees blocks **with build .3 showing on the title screen**, ask for a screenshot of `twinfang.html?nan`. Its readout gives invalid-pixel counts for the raw scene and for the frame handed to the final pass. Scene > 0 with final = 0 would mean the guard works and the blocks come from somewhere after it. Final > 0 would mean the guard itself fails on Direct3D. Candidates not yet ruled out on real hardware: GTAO output, and half-float overflow from very sharp highlights.
   Quick isolation switches: `?noao` (no ambient occlusion), `?q=low` (no AO, no MSAA, half-size textures).
2. **Frame rate unknown.** A fight costs roughly 2,000 draw calls per frame across the shadow, main and AO passes, about the same as the old version plus the AO pass. If it is slow: characters use up to 7 materials per bone, so merging shell colours through vertex colours would cut calls; GTAO could run at half resolution.
3. **Animation pass not done.** Player and boss clips in `08-clips` are untouched. This was held back on purpose until the owner has played the new build and said what feels off. The clips are keyframed poses in a 33-float format (`P({...})`, `K([...])`); the spring layer already adds overlap, so the work is mostly anticipation and recovery poses.
4. **Hero design is a first pass.** Slim android proportions, pale shell, dark tail plates, teal glow. Readable, but simpler than the level around it. The owner has not commented on it yet.
5. **Lantern and Stormvane** were not remodelled, only re-textured.

## Working rules learned the hard way

- **Bump `BUILD` in `src/01-util.js` with every delivered change**, and tell the owner which number to look for. During this session a fix was reported as delivered while the old files were still on disk; the stamp exists so that cannot go unnoticed again.
- **Rebuild after every edit** (`python build.py`). The owner opens `twinfang.html`, not `src/`.
- **Clamp before `pow`, `sqrt`, `normalize` and division** in every shader. See the shader rule in `README.md`.
- **A pass on the software renderer is not a pass on Direct3D.** Say so when reporting results, and ask the owner to look.
- **Do not change `AREAS`, hit timings or damage numbers casually.** They were tuned by play before this rebuild.
- Line endings: the repository stores LF; the Windows checkout has CRLF (`core.autocrlf`). `build.py` reads either and writes LF.

## Useful commands

```bash
python build.py                                   # src/ -> twinfang.html
node tools/run.mjs tools/s_bot.mjs                # must end: RUN COMPLETE, errors: 0
node tools/run.mjs tools/s_nan.mjs                # must end: NAN CHECK PASSED
node tools/run.mjs tools/s_audio.mjs              # bad: []
node tools/run.mjs tools/s_scenes.mjs --only cor,roof
node tools/run.mjs tools/s_show.mjs --kinds "hero:30:d=2.5;h=1"
```

Setup for the tools is in `tools/README.md`. On this PC they should run on the real GPU, which is exactly the coverage the earlier session lacked: once they work, `s_nan.mjs` and the screenshot scenarios become trustworthy checks for the Direct3D-only class of bug.
